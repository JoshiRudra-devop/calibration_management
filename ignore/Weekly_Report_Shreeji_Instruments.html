D25DIT088Abstract
Abstract

The rapid digitalization of industrial processes has created a pressing need for organizations to replace manual, paper-based workflows with efficient, accurate, and auditable digital systems. Shreeji Instruments, a calibration services firm, previously relied on entirely manual certificate creation processes — a workflow that was time-consuming, error-prone, and lacked systematic record-keeping or retrieval capabilities.

This report documents a four-week summer internship (June 2 – June 28, 2026) during which a comprehensive web-based Calibration Certificate Management System was designed, developed, tested, and deployed for Shreeji Instruments. The system is built using PHP 8 with PDO on a XAMPP/Apache server, MySQL as the relational database engine, and vanilla JavaScript with the jsPDF library for client-side PDF generation. Cloud-based PDF storage is achieved through the Cloudinary API.

The system supports twenty-six distinct instrument types including Auto Level, Cube Testing Machine (CTM), Vernier Caliper, Digital Thermometer, Oven, Water Bath, Hydrometer, and Total Station, among others. Each instrument type has a dedicated, structured certificate form with custom fields appropriate to the calibration parameters of that instrument. Key features include session-based user authentication with CSRF token protection and login rate limiting, an automated certificate numbering scheme with monthly resets and concurrent-safe row locking, a real-time dashboard with statistics and six-month trend charts, a due-date tracking module for recalibration reminders, an offline-first architecture using the File System Access API for field use, and a soft-delete and audit logging system for data integrity.

Security was a primary design concern throughout the project: all database interactions use PDO prepared statements, user passwords are hashed with bcrypt at cost factor 12, all form submissions include CSRF tokens verified server-side, and input is sanitized before display to prevent cross-site scripting.

The completed system successfully replaces the manual certificate workflow, significantly reducing issuance time and providing a searchable, cloud-backed digital archive of all calibration records. This project provided substantial hands-on experience with full-stack web development, relational database design, cloud service integration, and software security practices.

Keywords: Calibration Certificate, PHP, MySQL, jsPDF, Cloudinary, Web Application, PDF Generation, CSRF, Soft Delete, Audit Log, Instrument Management.

Chapter 1 Introduction

1.1     Background and Motivation

Calibration is the process of comparing the measurements of an instrument against a known reference standard to determine its accuracy. In industries such as civil engineering and construction, calibrated instruments are essential for ensuring the safety, quality, and compliance of materials and structures. A formal calibration certificate is issued after each calibration procedure, serving as documented proof that an instrument meets the required accuracy specifications.

Prior to this project, Shreeji Instruments managed the entire certificate issuance process manually. Technicians filled out printed forms or used word-processing templates for each calibration. This approach suffered from several significant drawbacks:

  • High manual effort for repetitive data entry across certificate fields
  • Absence of a centralized, searchable record of all issued certificates
  • Difficulty in tracking instrument recalibration due dates, leading to missed renewals
  • No systematic backup or cloud storage of issued certificates
  • Inconsistent certificate numbering without a formal tracking scheme
  • Inability to quickly retrieve historical certificates for audits or client queries

The growing volume of calibration requests and the increasing expectation from clients for digital records and prompt certificate delivery made it imperative to develop a purpose-built software system. This internship project addresses these gaps by delivering a complete web-based Calibration Certificate Management System.

1.2     Project Objectives

The primary objective of this project was to design and implement a full-featured web application that digitizes and automates the complete calibration certificate lifecycle for Shreeji Instruments. The specific objectives were:

  1. Develop a secure, role-based user authentication system to restrict access to authorized personnel.
  2. Create structured digital certificate forms for all twenty-six instrument types handled by the organization.
  3. Implement automated, concurrent-safe certificate numbering with a standardized format and monthly sequential reset.
  4. Enable client-side PDF generation with official letterhead, stamp, and signature images embedded in the output.
  5. Integrate cloud storage via the Cloudinary API to host issued certificates and provide shareable links.
  6. Build an administrative dashboard with statistical summaries, historical records, and due-date alerts.
  7. Implement an offline-first saving mechanism using the File System Access API for use in low-connectivity field conditions.
  8. Apply robust security measures including CSRF protection, SQL injection prevention, and bcrypt password hashing.
  9. Design a maintainable database schema with audit logging and soft-delete capability for data integrity.

2.5     Development Environment Setup

The development environment was set up on a Windows machine using the XAMPP software stack, which bundles Apache, MySQL, and PHP in a single installation package.

2.5.1   Environment Configuration

  • XAMPP: Installed and configured with Apache and MySQL services. The project folder was placed in C:\xampp\htdocs\calibration certificate\, making it accessible at http://localhost/calibration%20certificate/.
  • MySQL Database: Database shreeji_instruments created via phpMyAdmin. The database.sql file was imported to create all nine tables with seed data.
  • Cloudinary Account: A Cloudinary account was configured with an unsigned upload preset for the application. API keys were stored in includes/config.php.
  • PHP Configuration: display_errors was set to Off to prevent sensitive error information from leaking to the browser. Error logging was routed to the PHP error log file.

2.5.2   Version Control and Backup Strategy

A backup strategy was established using compressed archives stored in a separate folder (C:\xampp\htdocs\calibration_backups\). A full project backup was created before any major changes using a .tar.gz archive, along with restore scripts in both Windows Batch (restore.bat) and PowerShell (restore.ps1) formats to enable one-command restoration.

2.5.3   Key Design Decisions Made in Week 1

  • No PHP framework: The decision to use plain PHP without a framework (no Laravel, no Symfony) was driven by the goal of keeping deployment simple — any shared hosting with PHP 7.4+ and MySQL would be sufficient.
  • Client-side PDF generation: Rather than generating PDFs on the server (which would require a PHP PDF library and server-side form processing), jsPDF was selected for client-side generation. This reduces server load and allows real-time preview in the browser before saving.
  • Cloudinary over local storage: Storing PDFs on Cloudinary rather than the local server ensures certificates are accessible from any device with an internet connection, and protects against data loss from local disk failure.
  • Separate includes folder: All shared PHP code was planned in an includes/ directory, protected by an .htaccess file denying direct browser access — a security measure enforced from the design phase.

3.2     Authentication Module

The authentication module was implemented using PHP native sessions. The system uses phone number as the unique login identifier, which aligns with the company's preference (phone numbers are more reliably remembered by field staff than email addresses).

3.2.1   Login Page (login.php)

The login page renders a minimal, centred form with two fields: a 10-digit phone number and a password. The form submits via an asynchronous fetch() call to api/auth.php with a JSON payload. This prevents full-page reloads and allows inline error display. A CSRF token, embedded in the page via the SHREEJI_CONFIG JavaScript object output by header.php, is included in every request.

3.2.2   API Authentication Endpoint (api/auth.php)

The authentication API endpoint handles three operations: POST for login, GET ?action=logout for session termination, and GET ?action=check for session validation.

On login, the endpoint first enforces rate limiting using a per-IP counter stored in the PHP session under the key rl_{md5(ip)}. A maximum of five failed attempts are permitted within a fifteen-minute window. After a successful login, the rate-limit counter is reset, session_regenerate_id(true) is called to prevent session fixation attacks, and the user record is stored in $_SESSION['user'].

The API endpoint was carefully designed with error suppression (ini_set('display_errors', '0')) as its very first line — placed before even the require_once config.php statement — to ensure that no PHP warning or notice could corrupt the JSON response body and cause a parse error on the client side.

3.2.3   Central Configuration (includes/config.php)

All shared utilities were consolidated in includes/config.php. This file is the single point of inclusion required at the top of every PHP page. It provides:

  • getDB(): Returns a singleton PDO connection with ERRMODE_EXCEPTION and utf8mb4 character set.
  • requireLogin(): Checks $_SESSION['user_id']; redirects to login.php for page requests, or returns a JSON 401 response for API calls (detected by inspecting request headers).
  • csrfToken(): Generates and returns a 32-byte hex token stored in $_SESSION['csrf_token'].
  • verifyCsrf(): Validates the CSRF token from the X-CSRF-Token header or the request body.
  • clean(): Trims whitespace, strips HTML tags, and escapes special characters.
  • jsonResponse(): Sets Content-Type to application/json and outputs the encoded response.

3.3     Dashboard and Statistics

The dashboard (dashboard.php) is the primary management interface for the application. It was designed to give administrators an at-a-glance view of the system's state without requiring navigation through multiple pages.

3.3.1   Statistics Cards

Four summary cards are displayed at the top of the dashboard: total certificates issued, total unique parties registered, total instrument types configured, and certificates issued in the current month. These values are fetched from the database via api/contact.php?action=stats at page load.

3.3.2   Due Date Alerts

Below the summary cards, three alert counters display instruments that are overdue for recalibration, due within the current week, and due within the current month. These are calculated by querying certificates.next_due_date against the current server date.

3.3.3   Certificate History Table

A server-paginated table (50 rows per page) displays all issued certificates with filter controls for: date range (today, this week, this month, this year, custom), instrument type, party name, and due status. The table supports client-side text search across party name, certificate number, and site location fields.

3.4     Party and Company Management

The parties module manages the records of all client companies and organizations for whom certificates are issued. The companies.php page renders a searchable, sortable list of all parties with their contact details, site locations, and the number of certificates issued to each.

3.4.1   Auto-Create Pattern

Rather than requiring administrators to pre-register companies before creating certificates, the system automatically creates a party record the first time a new company name is entered in a certificate form. The api/save_certificates.php endpoint performs a case-insensitive lookup (WHERE LOWER(name) = LOWER(?)) before saving. If no matching party is found, a new record is auto-inserted. This eliminates administrative overhead and reduces friction during certificate creation.

3.4.2   Autocomplete via API

3.5     Certificate Numbering System

A well-designed certificate numbering scheme was identified as a critical requirement. Each certificate number must be unique, human-readable, traceable to a time period and instrument type, and generated without race conditions in a concurrent environment.

3.5.1   Number Format

Fig 3.2     Certificate Number Format Breakdown    (Example: CTM-260601)

Each instrument type has a unique prefix stored in the certificate_counter table (e.g., CTM for Cube Testing Machine, AL for Auto Level, VC for Vernier Caliper). The two-digit year and month are appended, followed by a zero-padded sequential number that resets to 01 at the start of each calendar month.

3.5.2   Concurrent Safety

To prevent two simultaneous certificate saves from receiving the same number, the counter update is wrapped in a database transaction with a SELECT ... FOR UPDATE row lock. This ensures that only one process can read and increment the counter for a given instrument type at a time, making the number generation fully atomic and safe under concurrent use.

3.5.3   Preview Without Increment

The api/get_next_certificate_number.php endpoint allows the front end to display what the next certificate number will be (for the user's reference before saving) without actually incrementing the counter. This is implemented as a read-only calculation based on the current counter state, with no locking required.
